# redteam

On-demand, sandboxed Claude Code (Fable) sessions for **authorized** red-team
assessment of this cluster and the services it hosts.

> **First draft / scaffold.** Items marked `TODO` are decisions or secrets you must
> supply. Nothing syncs until you wire up the ArgoCD Application, build the image,
> and provide the VPN.

## What this is

Two isolated red-team session pods. You attach with `kubectl exec` (no web UI,
no ttyd, no CloudTTY) — access control is just your existing cluster RBAC on
`pods/exec` in this namespace:

```
kubectl exec -it deploy/redteam-internal -n redteam -- tmux new -A -s rt
kubectl exec -it deploy/redteam-external -n redteam -c session -- tmux new -A -s rt
# then, inside: claude --model fable   (paste files/roe-<scenario>.md as the 1st msg)
```

`kubectl exec -it` allocates a real PTY, so the Claude TUI renders correctly.
Running inside `tmux` means a dropped connection doesn't kill the session — just
re-exec and it reattaches. Both Deployments are `replicas: 0`; scale to 1 per
engagement, back to 0 after.

| Scenario | Pod | Network origin | Repo | Simulates |
|----------|-----|----------------|------|-----------|
| **external** | Deployment + Gluetun VPN sidecar | Public internet (via VPN) | blind | Internet attacker hitting your port-forwarded services |
| **internal** | Deployment (repo pre-cloned) | Cluster/LAN (`10.69.x`) | pre-cloned | Attacker who joined your home network |

## The "oracle" boundary (read this)

Both sessions hold a **`view` ClusterRole** (read-only kube API, excludes secrets).
That's internal reachability a real attacker wouldn't have, so the ROE prompts frame
it as an **out-of-band situational-awareness oracle**: read it to plan, never count
it as attack surface reached. On the external pod, Gluetun's `FIREWALL_OUTBOUND_SUBNETS`
carves the kube API ClusterIP out of the tunnel; everything else (all attack traffic)
stays external.

## Authorization / safety design (hash-commitment nonce)

Fable verifies, before acting, that whoever provisioned the session controls `msng.to`:

1. **mittwald** generates a high-entropy `NONCE` in-cluster (`nonce-secret.yaml`); the
   raw nonce is injected into the pods as `$NONCE` and **never committed** to the repo.
2. The **hash is published automatically**: the `redteam-wellknown` init container
   reads the nonce, computes `sha256(NONCE)`, and substitutes it into the served
   `security.txt` — no manual step, and the pod won't start until the nonce exists.
3. Fable reads `$NONCE`, hashes it, and confirms it equals `X-RedTeam-Auth-SHA256` in
   `https://msng.to/.well-known/security.txt`.

A passive reader of the public file sees only the hash, so cannot forge a session.
To rotate: delete the `redteam-nonce` secret (mittwald regenerates) and restart the
`redteam-wellknown` pod so it re-hashes.

### Serving security.txt publicly

`security.txt` is served by a tiny nginx (`wellknown.yaml`) — no dependency on
homepage's asset handling. Since oauth2-proxy is the catch-all front door for msng.to,
its config (`k8s/platform/oauth2-proxy/values.yaml`) **already** skips auth for
`/.well-known/` and routes it to this static server (`skip_auth_regex` + an extra
`upstreams` entry). Just confirm `oauth2ProxyNamespace` in values.yaml matches the
oauth2-proxy namespace so the well-known NetworkPolicy allows its ingress.

## Network origin — the VPN (external scenario)

The external pod routes **all** attack traffic through a Gluetun killswitch so it
arrives at msng.to from a real internet IP (and split-horizon DNS resolves to your
public addresses).

**Don't use a commercial VPN (e.g. ProtonVPN):** its egress IPs are almost certainly
already in your CrowdSec block lists, so the pod would be pre-banned and the test ends
before it starts. (Worth noting as a finding — commercial-VPN ranges *are* blocked —
but useless as an origin.) **Recommended:** stand up a throwaway **WireGuard endpoint
on a cheap VPS** (DigitalOcean/Hetzner/Fly; `wg-easy` makes this ~5 min) and point
Gluetun at it in `custom` mode (`values.yaml gluetun.env`). You control that IP, it's
not on VPN block lists, and you can decide whether to whitelist it in CrowdSec to test
*past* the IP-reputation layer or leave it to exercise the full stack.

## Prerequisites

1. **Session image** with `claude`, `kubectl`, `git`, recon tools — see `files/Dockerfile`.
   Build, push, set `image` in `values.yaml`.
2. **Secrets** (create manually or via your SOPS flow):
   - `redteam-anthropic` — `ANTHROPIC_API_KEY` (scope + rotate; egress policy is the backstop).
   - `redteam-vpn` — `WIREGUARD_PRIVATE_KEY`, `WIREGUARD_ADDRESSES` for your VPS endpoint.
   - `redteam-nonce` — auto-generated by mittwald; nothing to create.
3. **Confirm** `kubeApiCidr` (`kubectl get svc kubernetes -n default`) and `oauth2ProxyNamespace`.
4. **Wire up ArgoCD** — add `application.yaml` to your app-of-apps.

_The oauth2-proxy `/.well-known/` change is already applied in
`k8s/platform/oauth2-proxy/values.yaml`._

_No Gitea credential is needed — the repo is unauthenticated-readable and the internal
pod pre-clones it in an init container._

## Cost / audit / teardown

- **Cost:** set a turn/spend ceiling in the prompt (`<N>`/`<$X>` placeholders); Fable loops burn tokens.
- **Audit:** enable kube-apiserver audit logging for these SAs; capture the tmux transcript (`tmux pipe-pane`).
- **Teardown:** scale Deployments to 0, delete `redteam-nonce` to rotate the nonce between engagements, or delete the namespace to nuke everything.

## Verify the external egress BEFORE trusting it (load-bearing)

The Gluetun killswitch + NetworkPolicy is what makes "external" actually external and
stops a confused/injected agent from pivoting or exfiltrating. From inside the running
external pod's `session` container:

```
curl -s https://api.ipify.org          # must be the VPS/VPN IP, NOT your home IP
curl -s --max-time 5 https://git.msng.to || echo "internal blocked (good)"
kubectl get ns                          # oracle works (kube API carve-out)
```

- **CrowdSec whitelist the VPS IP?** Full-stack test vs. testing past IP reputation — your call per run.
- **Tighten internal egress** from "all 443" to Anthropic ranges if desired.
