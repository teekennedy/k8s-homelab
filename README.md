# Kubernetes Homelab

This repo manages my bare metal k8s cluster I've setup in my basement. I built this to reduce my subscriptions through self-hosted services, to deepen my understanding of kubernetes and NixOS, and to have a space to experiment with new tooling and methodologies.

# Goals and Features

- **Infrastructure as code maximalism**
  - **Immutable hosts**: All hosts are declaratively configured using NixOS. Nix impermanence takes this a step further by _wiping the root subvolume on every boot_. This keeps the system fresh, counteracts configuration drift, and forces 100% infrastructure as code. I have a small set of subdirectories that persist across reboots for caching and backup purposes.
  - **OpenTofu-managed external secrets**: External secrets such as SMTP creds and access keys for CloudFlare DNS management are all owned and managed by OpenTofu modules and injected into the cluster using the kubernetes provider. Input variables and state files are encrypted with sops.
  - **CUE as the source of truth for cluster topology**: environment config is declared once and fanned out into Nix, Helm, and Terraform. No need to hand-duplicate IP ranges or host lists across three tools.
- **Zero-touch setup and maintenance**
  - **Self-provisioning services**: Various custom sync jobs automate the runtime configuration of services and intra-cluster integrations:
    - The [Forgejo resources](/k8s/platform/forgejo/templates/forgejo-resources.yaml) sync job automatically provisions users, organizations, repos, and SSO integrations.
    - NixOS hosts automatically form a Nix build cluster and sign packages with an auto-generated key.
    - OIDC clients are automatically integrated with Authelia using a custom sync job.
  - **Self-updating dependencies**: Dependencies are updated by Renovate, CI checked by Woodpecker, and auto-merged once checks pass. Major version upgrades are exempted from auto-merge.
  - **Continuous delivery**: Once a change lands in `main`, it is auto-deployed based on the type of change. Changes to kubernetes resources are handled by ArgoCD. Changes to NixOS hosts are handled by a custom systemd unit that builds a new system derivation, sets it to activate on the next boot, and triggers [kured](https://kured.dev/) to gracefully reboot the node.
  - **Autogenerated internal secrets**: Host-specific secrets are autogenerated with the `lab host bootstrap` command, which generates secrets for the host, then configures sops to encrypt them using the host's SSH key. Kubernetes secret values are autogenerated upon secret resource creation using [kubernetes-secrets-generator], and, if needed, copied across namespaces using [kubernetes-reflector]. This provides automatic setup and easy rotation of secrets.
  - **Automatic split horizon dynamic DNS**: External DNS automatically manages public A records on CloudFlare, internal A records on Unifi. A custom dynamic DNS controller polls for changes to the external IP address and reconfigures / reloads external DNS automatically.
- **Defense in depth**
  - **Link layer network access control**: LAN facing services use a separate load balancer VIP and Traefik Gateway from publicly accessible ones, enabling network access to be enforced through routing and firewall rules. Publicly exposing a service requires two separate configuration opt-ins, making it difficult to do accidentally.
  - **WAF-protected public endpoints**: [Crowdsec](https://www.crowdsec.net/) is setup and integrated as a Traefik middleware to act as a WAF (Web Application Firewall) for all publicly exposed services. While it would be nice to use CloudFlare Tunnels for this purpose, it is against CloudFlare's ToS to use their networks for streaming media. Since I run a Jellyfin instance, I had to find another solution.
  - **Kernel-native mutual TLS auth for NFS**: Using RFC 9289 `xprtsec=mtls` for encrypted and authenticated NFS mounts. Cert-manager issues per-node certs from an internal CA and a DaemonSet that hot-reloads the host's `tlshd` for fullly automated cert generation and rotation.
  - **Proactively red-teamed**: A sandbox provides an AI agent with cluster read access, a local clone of the public k8s-homelab repo, and a full tunnel VPN connected to a public server to simulate attacks from the internet at large. Red-teaming is authorized through a hash-commitment scheme. A secret nonce is hashed into a public `security.txt` (RFC 9116). The agent is provided with this nonce and told to check that the hashes match to prove that it is authorized to red-team the domain.
- **Accelerated agentic development**
  - **Backpressure**: linters and validation tools that provide _automated pushback_ to correct and guide AI-generated code so you don't have to. For example, golangci-lint has linters to ensure go code is formatted nicely, uses modern idioms, and doesn't fall into security pitfalls. Polaris and Kubeconform ensure that all new k8s resources are using industry best practices. are running rootless with a read-only filesystem, a defined NetworkPolicy, and no unnecessary capabilities.

# Setup

## Bootstrapping a NixOS Host

See [docs/nix-host-bootstrap.md](docs/nix-host-bootstrap.md) for the full guide.

Quick start:

1. Add the host to `flake.nix` in the `borgHosts` list
2. Build and boot the installer ISO: `nix build .#nixosConfigurations.installIso.config.system.build.isoImage`
3. Run: `lab host bootstrap <hostname> --ip <installer-ip>`

The bootstrap command handles secrets generation, sops configuration, hardware detection, NixOS build verification, and installation automatically.

## Deploying updates

Use deploy-rs: `deploy -- .#borg-0`

If you just want to build the nixosSystem for a host (e.g. to test configuration changes), run `nix build -L .#nixosConfigurations.borg-0.config.system.build.toplevel`. `-L` outputs build logs to stderr.

## Bootstrapping k3s cluster

Start your first k3s server with `services.k3s.clusterInit = true;`. See nix/modules/k3s/k3s.nix for a full example.

Once applied, log into the host and check that k3s is running with `sudo systemctl status k3s.service`. Check the k3s logs for errors as well `sudo journalctl -fu k3s.service`.

Run the helper script from the scripts directory to fetch all certificates, keys and tokens and write them encrypted with sops to ./nix/modules/k3s/secrets.enc.yaml

Also copy /etc/rancher/k3s/k3s.yaml from the first node and place it in ./.devenv/state/kube/config in this repo (will be gitignored). You'll need to replace `server:` with the server's actual address (not 127.0.0.1).

### Longhorn

Run `lab k8s bootstrap --env production` to install foundation components including Longhorn.
